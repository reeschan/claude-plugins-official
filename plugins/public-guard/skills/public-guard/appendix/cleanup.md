# 公開リポジトリに出てしまった語の後始末

ガードが止めきれずに (ガードを入れる前や、人の手の操作で)、公開リポジトリへ外に出したくない語が出てしまったときの手順。直すかどうか、どこまでやるかは持ち主が決める。Agent は、GitHub の画面での操作と Support への依頼をしない (持ち主がする)。

GitHub の画面の名前と Support の受付の内容は変わることがある。使う前に GitHub の文書「Removing sensitive data from a repository」と「Tracking changes in a comment」で、今もそうかを確かめる。

## どこに残っているかを調べる

`public-guard.mjs audit` (自分の公開リポジトリすべて) か `audit --repo owner/repo` で、HEAD のファイル・全ブランチのコミットメッセージ・PR と issue のタイトルと本文を報告する。次の 3 つは audit では見ないので、目で確かめる。

- PR・issue のコメント、レビューのコメント
- 編集履歴に残っている古い版
- force-push 前のコミット

## 今の版を直す

- **ファイル**: 一般化した文に直してコミットする。履歴にも残したくなければ、次の「履歴から消す」へ進む。
- **PR・issue の本文とコメント**: 一般化した文に書き換える。書き換えただけでは、古い版が編集履歴に残る (「編集履歴から古い版を消す」へ)。
- **リリースノート**: 書き換える。

## 履歴から消す (コミットに入ってしまったとき)

1. その公開リポジトリを使っているほかの作業 (worktree・clone・開いている PR のブランチ) を書き出す。
2. `git filter-repo --replace-text <置き換えの一覧>` か `git rebase -i` で、該当するコミットのメッセージと中身を書き換える。置き換えの一覧はリポジトリの外に置く。
3. 全ブランチとタグを `git push --force-with-lease` で書き換える。持ち主がその場で許したときだけ流す。
4. ほかの clone と worktree は、`git fetch` のあと、自分のコミットだけを新しい履歴の上に載せ直す (`git rebase --onto origin/<既定ブランチ> <古い既定ブランチ> <ブランチ>`)。古い履歴のまま push すると、消した内容が戻る。
5. フォークがあれば、フォークの中身は消えない。フォークの持ち主に頼むか、Support への依頼に含める。

## 編集履歴から古い版を消す (PR・issue の本文、コメント)

1. 本文やコメントの上にある「edited」の印を押し、編集履歴を開く。
2. 消したい版を選び、「Delete revision from history」で消す。版ごとに繰り返す。
3. 最初の版 (作ったときの本文) も消せるかを確かめる。消せないときは Support に頼む。

## GitHub Support に頼む (force-push 前のコミット、キャッシュ)

force-push しても、前のコミットは SHA の URL や PR の「force-pushed」の記録から開ける。これを消せるのは GitHub Support だけ。

1. support.github.com から、リポジトリの持ち主として依頼を出す。
2. 書くこと: リポジトリ名、消したいコミットの SHA (force-push 前のもの)、関係する PR の番号、「機密の情報を履歴から消した。キャッシュされた表示と、PR から参照される古いコミットを消してほしい」という依頼。
3. 依頼の文にも、消したい語そのものは書かない。SHA と場所だけで足りる。

## 終わったら

- もう一度 `audit` を流し、ヒットが消えたことを確かめる。
- 漏れた原因が一覧の抜けなら、`~/.config/public-guard/deny.txt` に語を足す (持ち主が確かめてから)。
- 原因が Agent の書き方 (語では照らせない業務の内容など) なら、`CLAUDE.md`・`AGENTS.md` の決まりを見直す。
