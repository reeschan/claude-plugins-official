# public-guard

このプラグインのフックは、Agent が公開リポジトリへ文を出す操作 (commit・push・PR や issue・リリース・公開 gist・`gh api` の書き込み・公開への切り替え) の直前に、外へ出る文を手元の一覧で照らし、語があれば止める。このスキルは、その一覧を作り、ガードの状態を確かめ、すでに出てしまったものの片付けを案内する。

スクリプトは `${CLAUDE_PLUGIN_ROOT}/scripts/public-guard.mjs`。以下では `PG` と書く。Bash では `node "${CLAUDE_PLUGIN_ROOT}/scripts/public-guard.mjs" <入口>` で呼ぶ。

## いつも守ること

- 一覧 (`~/.config/public-guard/` の `deny.txt`・`auto.txt`・`exclude.txt`・`allow/`) は手元にだけ置く。どのリポジトリ・PR・issue・gist・外のサービスにも、写しも一部も書かない。一覧そのものが、外に出したくない文脈だから。
- 一覧の語を見せるのは、ユーザーとのこの会話と、リポジトリの外の手元のファイルだけにする。
- 許可リスト (`allow/<owner>__<repo>.txt`) は、ユーザーが「入れて」と言ったときだけ書く。止まった操作を通すために Agent が自分で書き足さない。
- フックに止められたら、語を一般化して書き直す (例:「ある組織のリポジトリで、PR 本文の検査が…」)。コマンドを分ける・スクリプトのファイル経由で git を呼ぶ・環境変数を付けるなどで避けない。どうしても出す必要があると考えるなら、操作する前にユーザーに確かめる。
- 引数が無ければ、`doctor` を流して状態を伝え、次にどれをするかをユーザーに聞く。

## setup: 一覧を作る

1. `PG doctor` を流し、node・gh・今の一覧の状態を伝える。
2. `PG init` で置き場所と空のひな形を作る (既にあれば触らない)。
3. 所属組織があれば `PG refresh` で自動の一覧 (組織の名前とそのリポジトリ名) を作る。6 文字以下の名前は誤検知が多いので、初めから `exclude.txt` に入る。組織の数と語の数を伝える。
4. 手書きの一覧の候補を集める。ユーザーに、外に出したくないもの (会社・顧客・製品の名前、社内のツールやスキルの名前、案件の番号の形など) を聞く。手がかりとして、自動の一覧のリポジトリ名の頭の部分 (顧客名や製品名のことが多い) や、手元にある組織のリポジトリの名前を使ってよい。
   - 候補は、リポジトリの外の手元のファイルか、この会話でだけ見せる。
   - ありふれた英単語や短すぎる語は、誤検知で作業が止まるので候補から外すか、ユーザーに確かめる。
   - 番号の形の正規表現 (`re:` で始める) は、ユーザー自身の命名 (作業の番号など) とぶつからないかを確かめてから入れる。
5. ユーザーが確かめた語だけを `deny.txt` に書く。先頭のコメントに、作った日と「持ち主が確かめた」ことを書く。
6. 誤検知を測る。`PG audit` (自分の公開リポジトリすべて) か `PG audit --repo owner/repo` を流し、ヒットを伝える。正しく出してよいもの (例えば自分の公開リポジトリの名前と同じ語) は、`exclude.txt` から外すか、許可リストに入れるかをユーザーに聞く。本当に漏れているものは `cleanup` を案内する。
7. `~/.codex` があれば `PG codex-install` を流す (Codex にはプラグインが無いので、スクリプトを `~/.config/public-guard/bin/` に写してフックに登録する)。
8. `doctor` の手順で、ガードが本物の経路で効くことを確かめて終わる。

## audit: 残っている語を報告する

`PG audit` か `PG audit --repo owner/repo` を流す。HEAD のファイル・全ブランチのコミットメッセージ・PR と issue のタイトルと本文を照らし、ヒットの件数と場所を伝える。直すかどうかはユーザーが決める。PR や issue のコメント・編集履歴の古い版・force-push 前のコミットは見ないので、そう伝える。

## doctor: 状態を確かめる

1. `PG doctor` を流し、`要対応` の行をユーザーに伝える。直し方の目安:
   - 一覧に語が無い → `setup`。
   - Codex の登録が無い・写しの版が違う → `PG codex-install`。
   - Claude Code の設定に手で登録した同じガードがある → プラグインと二重に動く。外してよいかをユーザーに聞いてから、`~/.claude/settings.json` のその 1 件だけを消す。
2. `PG selftest` を流し、出てきた `git -C ... commit ...` のコマンドを、書き換えずに Bash でそのまま流す。一時のリポジトリの中だけで動き、外には何も出ない。
   - 「試し語を見つけたので止めました」で止まれば合格。
   - 「一覧がありません」で止まれば、フックは効いているが一覧がまだ無い。
   - 止まらずにコミットできたら、フックが効いていない。プラグインが有効か (`/plugin`)、`node` が PATH にあるかを確かめる。node が無いとフックは失敗し、Claude Code はそれを「止める」と読まないので、何も言わずに通る。

## cleanup: 出てしまったときの後始末

[付録 cleanup](${CLAUDE_SKILL_DIR}/appendix/cleanup.md) を読み、ユーザーと一緒に進める。GitHub の画面での操作と GitHub Support への依頼はユーザーがする。履歴の書き換えと force-push は、ユーザーがその場で許したときだけする。
